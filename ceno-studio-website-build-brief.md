# Ceno Studio — Website Build Brief

## Build objective

Preserve the existing Ceno visual identity and interaction language, while changing the public brand from **Ceno Labs** to **Ceno Studio** and repositioning the business as a **solo protocol engineering studio focused on onchain finance**.

| Item | Decision |
| --- | --- |
| Canonical domain | `ceno.studio` |
| Legacy domain | `ceno.dev` → 301 redirect to `ceno.studio` |
| Public brand | Ceno Studio |
| Legal entity | Ceno Labs Ltd |

### Reference sites

- **Current Ceno site:** use `ceno.dev` as the visual-language baseline.
- **Vayu Apps:** use as a reference for the clarity of a founder-led / solo-studio structure.
- Do **not** copy Vayu's design or wording.

---

# 1. Positioning

## Core proposition

# Onchain finance, engineered end to end.

A solo protocol studio helping teams design, build and launch onchain financial systems.

Protocol architecture, smart contracts, interfaces and infrastructure — from idea to production.

## What Ceno should feel like

- A serious independent engineering practice, not a generic Web3 agency.
- One senior builder with deep protocol experience and direct technical ownership.
- Technical, understated, precise and confident.
- Small by design; no attempt to look like a larger team.

## Voice

- Use **“I”** when describing how engagements work and what the founder does.
- Use **“Ceno”** when describing the studio, products or case-study outcomes.
- Avoid corporate **“we”** language unless it genuinely refers to a collaboration.
- Avoid phrases such as **“our team”**, **“full-service agency”**, **“we scale teams”**, or anything implying a hidden delivery team.

## Ideal clients

- Founders building new onchain financial products.
- Funded protocol teams that need senior ownership for a build, upgrade, migration or launch.
- L1/L2 ecosystems and foundations that need financial infrastructure.
- Existing teams that need a fractional protocol lead rather than a full-time hire.

# 2. Brand migration

This is an evolution of the existing `ceno.dev` site, not a visual rebrand.

## Keep from ceno.dev

- Existing typography, palette, spacing system and visual design tokens.
- Numbered sections and compact uppercase metadata.
- Monospace / terminal-style system labels.
- Technical diagrams, schematics and infrastructure graphics.
- Grid, border and panel language.
- Restrained motion and system-status motifs.
- The technical project-intake form treatment.

## Change

- `CENO LABS` → `CENO STUDIO`.
- Broad finance / payments / AI positioning → onchain finance and protocol engineering.
- Large-company tone → solo-studio tone.
- Generic capability buckets → concrete ways to work with Stephen.
- Featured work → Symmetric, DataDex × Vana and Setwise.
- Remove Regenerative and Cable from featured work.
- Revolv becomes supporting work rather than a flagship case study.

## Wordmark treatment

Use the same brand construction as the current site.

Replace the secondary label **LABS** with **STUDIO**.

Do not redesign the Ceno mark unless the existing implementation forces a change.

# 7. Case-study page template

All three case-study pages should use the same structure and feel like **technical project notes**, not glossy agency portfolio pages.

## Structure

1. Project label + one-line outcome.
2. Context / challenge.
3. Ceno's role.
4. What was built.
5. Technical depth / notable systems.
6. Outcome or current status.
7. Links:
   - live product;
   - source code;
   - relevant ecosystem references where appropriate.
8. Compact **“What this demonstrates”** capability line.

## Symmetric page emphasis

- Multi-chain protocol ownership.
- Balancer-based AMM infrastructure.
- Governance, gauges, emissions and rewards.
- Grant-funded work for Balancer and Tezos.
- Taiko 80/20 TAIKO/ETH lock-up and Trailblazers integration.
- Live migration / recovery experience can be included where appropriate and accurate.

- Built in collaboration with the Vana Foundation.
- Purpose-built exchange and liquidity infrastructure for Vana.
- DEX interface, liquidity management, routing, network integration, subgraphs and analytics.

# 8. Visual and interaction rules

## Do

- Reuse the current `ceno.dev` CSS tokens, type scale, grid, borders, spacing and motion wherever practical.
- Use technical schematics and diagrams as the primary visual language.
- Keep section numbers and system-style microcopy.
- Prefer strong typography and whitespace over decorative illustration.
- Use project screenshots only where they add evidence.
- Do not turn the site into a screenshot gallery.
- Keep interactions fast and restrained.

## Do not

- Introduce generic purple/blue Web3 gradients.
- Use stock imagery or generic 3D crypto renders.
- Add fake team language.
- Add fake client metrics.
- Add generic testimonials.
- Overload pages with animation.
- Create a conventional agency grid of dozens of capabilities.
- Make the site feel like a VC-backed startup or a 20-person development company.

## Responsive

- Preserve the technical identity on mobile rather than stripping it to plain text.
- Stack project cards and service blocks cleanly.
- Ensure terminal/system labels remain legible at small sizes.
- The project form must be easy to complete on mobile.
